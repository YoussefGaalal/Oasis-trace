1 Authentication (Sanctum)

1.1 Login & Token Flow

Oasis uses Laravel Sanctum's opaque token (not SPA cookie) strategy. On login, a plaintext token is created and returned to the client, which stores it (cookies in React, SharedPreferences in Flutter) and sends it as Authorization: Bearer {token} on subsequent requests.

POST /api/auth/login — Client sends email + password (+ optional language preference)

AuthController validates fields, queries users by email with User::where('email')->first()

Hash::check(password, user->password) — bcrypt comparison. Returns 401 on mismatch. Intentionally vague ("Invalid credentials") to prevent user enumeration.

$user->is_active checked — inactive accounts return 403 account_inactive

$user->createToken('auth-token')->plainTextToken — Sanctum creates a row in personal_access_tokens and returns the token

Response includes the token + a user payload (id, name, email, role, roles[], language, subscriptionTier). Token is NOT stored server-side in session — it is the credential.

On subsequent requests: Laravel's auth:sanctum middleware finds the token in the request header, looks up personal_access_tokens, hydrates the User, and makes it available via $request->user()

AuthController.php — login() key logic
// 1. Credential check
$user = User::where('email', $request->email)->first();
Hash::check($request->password, $user->password); // bcrypt

// 2. Active check
if (!$user->is_active) return response()->json([...], 403);

// 3. Token creation (Sanctum)
$token = $user->createToken('auth-token')->plainTextToken;

// 4. Role resolution (Spatie)
$user->getPrimaryRoleName(); // → getRoleNames()->first() ?? 'Owner'

1.2 Password Reset (Custom Implementation)

Laravel's built-in Password::sendResetLink() is imported but not used. Instead, a completely custom reset flow is implemented that stores tokens directly on the users table:

  • Token: Str::random(64) stored in users.password_reset_token
  • Expiry: users.password_reset_expires set to now()->addHours(24)
  • Email integration is commented out with a // TODO — the reset URL is currently returned directly in the API response as debug_url
Critical — Token in API Response Body: forgotPassword() returns the raw reset token as "debug_url" in the JSON response. This means the reset token is transmitted in clear JSON, visible in logs, proxies, and browser developer tools. Anyone who intercepts a forgot-password API call can obtain the reset token and hijack the account. The email integration must be completed and debug_url removed from the response.
Warning — Non-Standard Reset Storage: Laravel convention is to store reset tokens in the password_reset_tokens table (included by default in fresh installs). Storing them on the users table adds nullable columns to the main user record, wastes space for non-resetting users, and lacks the automatic cleanup that the built-in password broker provides.

1.3 The Header-Fallback Auth Pattern (X-User-Id / X-User-Role)

Nearly every controller uses the OwnableAuthorization trait, which contains a dual-path identity resolution system:

OwnableAuthorization.php — identity resolution
private function getUserId(Request $request): ?string
{
    // Path 1: Proper Sanctum token auth
    if ($request->user()) {
        return (string) $request->user()->id;
    }
    // Path 2: Plain HTTP header — anyone can forge this!
    return $request->header('X-User-Id');
}

private function getUserRole(Request $request): ?string
{
    if ($request->user()) {
        return $request->user()->getPrimaryRoleName();
    }
    // Path 2: Plain header — forge X-User-Role: Admin to escalate
    return $request->header('X-User-Role');
}
Critical — Privilege Escalation via Forged Headers: Because most routes lack auth:sanctum middleware, $request->user() returns null and the trait falls through to reading raw HTTP headers. Any caller can set X-User-Role: Admin and X-User-Id: 1 to impersonate the admin user. This completely bypasses the RBAC system. Fix: add auth:sanctum to all routes; remove the header fallback path once Sanctum is properly wired.

2 Module: Animals

2.1 Overview

The Animal module is the core entity. AnimalController handles CRUD, photo uploads, and ownership transfer. It uses the OwnableAuthorization trait for all access decisions and applies the limits:animals middleware for subscription enforcement. API Resources (AnimalResource) handle response shaping.

Key capabilities

  • Full CRUD with permission check (manage_animals) on write operations
  • Dual photo upload: multipart file upload OR base64-encoded data URI in JSON body
  • Role-aware owner assignment (Owner → self, Manager → managed_by owner, Admin → nullable)
  • Ownership transfer between Admin/Owner users with role validation
  • Eager-loads owner, device, groups, geofences on list queries

2.2 Photo Upload — Dual Strategy

The controller handles two completely different upload paths within the same request handler:

PathDetectionStorageConcerns
Multipart file$request->hasFile('identification_photo')storeAs → public/images/Correct approach; no size limit enforced in controller
Base64 data URIString starting with data:imagebase64_decode → Storage::put()Entire image travels in JSON body; no size limit; always stored as .png regardless of source type; no MIME validation; memory pressure on large images
Warning — Base64 Upload Path: Sending images as base64 strings inside a JSON payload inflates payload size by ~33%. There is no validation on image type, dimensions, or file size in the base64 path. A malicious actor could send a very large base64 string causing PHP memory exhaustion. The fix is to remove the base64 path entirely and enforce multipart/form-data uploads via StoreAnimalRequest.

2.3 Animal ID Generation — Race Condition

Animal IDs are generated in two places, and they conflict:

AnimalController::store() — ⚠️ race condition
// In the controller — uses COUNT(*) which races:
$data['animal_id'] = 'OA-' . date('Y') . '-' . str_pad(Animal::count() + 1, 4, '0', STR_PAD_LEFT);

// In Animal::boot() — correct approach using MAX(animal_id) per year:
$latest = static::where('animal_id', 'like', "OA-{$year}-%")
    ->orderByDesc('animal_id')
    ->first();

The controller sets $data['animal_id'] before calling Animal::create(), which then triggers the model's boot() hook — but the hook only runs if (empty($animal->animal_id)), so it's skipped. The controller's version uses Animal::count() + 1, which:

  • Produces duplicates under concurrent creation (two requests read count=100 simultaneously → both try to create OA-2026-0101)
  • Breaks after any deletion (count drops, next ID collides with a deleted one)
  • Resets the sequence cross-year incorrectly
Critical — Duplicate Animal IDs: Under concurrent usage, multiple animals can receive the same ID. The animal_id column has a UNIQUE index, so the second concurrent insert will fail with an unhandled database exception. Fix: remove the ID assignment from the controller entirely and let the Model's boot() handle it (it uses the correct MAX pattern). Better still: use a dedicated DB sequence or atomic counter.

3 Module: Geofencing

3.1 Overview

Two controllers handle geofencing: GeofenceController manages zone CRUD and alert management, and LocationHistoryController::store() is the GPS ingestion endpoint that triggers violation detection. The NotificationService dispatches alerts via SMS/WhatsApp/call.

The geofencing pipeline is entirely synchronous and runs inline with the GPS write request — meaning every GPS ping blocks the HTTP thread for the full duration of geofence checks and notification delivery.

3.2 Violation Detection Pipeline (Critical Path)

POST /api/location-history — GPS device sends device_id, latitude, longitude, speed, heading

Device lookup → find associated animal. Device::findOrFail() then Animal::find(device->animal_id)

Location row inserted into location_history table. Device row updated (gps_lat, gps_lng, last_ping, status='online')

checkGeofences(animal, lat, lng) called — fetches ALL active geofences from DB, then filters in PHP by owner_id match

For each geofence: look up cached state cache()->get("geofence_{id}_animal_{id}_inside"). If key not found → assume current state, skip alert on first ping.

Run Geofence::containsPoint(lat, lng) — pure PHP ray-casting algorithm. Compare with cached state.

If state changed (entry or exit matches alert_type): insert GeofenceAlert, call NotificationService::sendGeofenceAlert() synchronously

Inline cleanup: Deletes all location_history rows older than 5 hours for this animal — in the same request!

Critical — Geofence Query Fetches ALL Active Geofences: checkGeofences() calls Geofence::where('is_active', true)->get() — this loads every geofence in the system into memory, then filters by owner in PHP. As the platform scales, this will degrade to scanning thousands of geofences per GPS ping. Fix: query only geofences assigned to this specific animal using the pivot table.
LocationHistoryController.php — the scalability problem
// ❌ Current: Fetches ALL geofences from DB into memory
$geofences = Geofence::where('is_active', true)->get();
$geofences = $geofences->filter(fn($g) => $g->owner_id === $animal->owner_id);

// ✅ Better: Query only geofences assigned to this animal
$geofences = $animal->geofences()->where('is_active', true)->get();

// ✅ Best: Use DB spatial functions (requires migrating to GEOMETRY type)
// ST_Contains(geofence.polygon, ST_GeomFromText("POINT(lat lng)"))

3.3 NotificationService

The NotificationService is a concrete class (not a Laravel Notification) injected via constructor into both GeofenceController and LocationHistoryController. It dispatches alerts across three channels sequentially.

Warning — 6+ Synchronous DB Queries per Alert: getSetting(key) hits DB::table('settings')->where('key',...)->first() with a fresh query every call. It's called once for each of: twilio_account_sid, twilio_auth_token, twilio_phone_number, twilio_enabled, whatsapp_api_url, whatsapp_api_token, whatsapp_phone_number_id, whatsapp_enabled — totalling 8+ sequential DB hits before a single SMS is sent. Fix: cache settings with Cache::remember() for 5 minutes.
Warning — isSmsEnabled() and isCallEnabled() use the same setting key: Both methods check getSetting('twilio_enabled'). Enabling Twilio for SMS also enables voice calls. These should be separate boolean settings.

The alert message is hardcoded with a camel emoji: "🐪 Oasis Alert: {animal_id} has {entered|exited} {geofence_name}". This is species-specific branding that doesn't fit goat or sheep owners.

4 Module: Auctions

4.1 Overview

The auction module is the most complex in the backend — AuctionController is 714 lines and covers listing, bidding, payment processing (Stripe + bank transfer), winner management, and admin verification. The core business objects are Auction and Bid, with auction status flowing through: draft → active → sold/ended/cancelled.

Auction StatusMeaningPayment Status
draftCreated but not yet started—
activeLive, accepting bids—
soldWinner determined, awaiting paymentpending → submitted → verified/rejected
endedClosed without meeting reserve price or no bids—
cancelledManually cancelled by owner—

4.2 Bidding Logic

POST /auctions/{id}/bid — Validates amount >= current_price + 1 (minimum increment of 1 SAR)

Owner self-bid check: $auction->owner_id == $userId → 400 error

$auction->isActive() check: status === 'active' AND ends_at is in the future

Bid row created with amount, user_id, bidder_name, bid_at timestamp

$auction->update(['current_price' => amount]) — non-atomic update

Critical — Non-Atomic Bid Race Condition: Two simultaneous bids at amounts 510 and 520 SAR can both pass the amount >= current_price + 1 check (if current_price is 500), both be inserted, and both trigger the update(current_price). The winner would be whichever update runs last — but both bids exist in the DB. Auctions can end with a winner whose bid is not the actual highest. Fix: wrap the bid check + update in a DB transaction with a SELECT FOR UPDATE lock on the auction row.
Warning — No Bid Minimum Increment Flexibility: The minimum increment is hardcoded as current_price + 1 (1 unit of currency). For auctions with high-value livestock (e.g. 50,000 SAR camels), 1 SAR increments would create thousands of near-identical bids. Consider making the minimum increment configurable per auction.

4.3 Payment Paths

There is no scheduled artisan command or queue job to run this automatically. Auctions can remain in a "sold + pending" state indefinitely if no one calls this endpoint. 5 Module: Tasks

5.1 Overview

The task module coordinates livestock care work across the role hierarchy. TaskController handles CRUD and role-scoped filtering. TaskLogController manages completion evidence (photo, voice, GPS). The Task model contains the recurrence engine. Role-based filtering is implemented directly in controller methods rather than using model scopes consistently.

5.2 Recurrence Engine

The Task model implements recurring task logic via two methods:

Task.php — recurrence engine
calculateNextDueDate(): // Computes next due date based on recurrence_type
  'daily'  → addDays(interval)
  'weekly' → addWeeks(interval)
  'monthly'→ addMonths(interval)
  'custom' → iterates recurrence_days[] to find next weekday after current due_date

createNextOccurrence(): // Clones task with new due_date, resets status to pending
  // Called: on task CREATION if is_recurring=true
  // NOT called: on task completion ← Bug
Critical — Recurring Tasks Don't Actually Recur: createNextOccurrence() is called in TaskController::store() when a task is first created (creating one pre-scheduled next occurrence). But it is NOT called in complete() when a task is marked done. So after the pre-created occurrence is completed, the chain stops. The recurrence engine is half-built. Fix: call $task->createNextOccurrence() in the complete() action.
Warning — Validation Key Mismatch: TaskController::store() validates 'recurrence_pattern' but the Task model's fillable field and database column is named 'recurrence_type'. The validated value is never actually saved under the correct key. Add explicit mapping: $validated['recurrence_type'] = $request->recurrence_pattern.

7 Scalability Improvements

7.1 Immediate (Must Fix Before Load)

🔴 Queue Notifications Asynchronously

Every GPS ping that triggers a geofence alert blocks the HTTP response while sending SMS + WhatsApp + calls synchronously. Under load this will cause GPS device timeouts and dropped pings.

Set QUEUE_CONNECTION=redis, run php artisan queue:work, and dispatch SendGeofenceAlert::dispatch($alert) as a queued job.

🔴 Fix Geofence Query (Scope to Animal)

Replace the full-table geofence scan with a scoped relationship query:
$animal->geofences()->where('is_active',true)->get()

This turns an O(total_geofences) scan into an O(animal_geofences) lookup — orders of magnitude faster at scale.

🔴 Switch Cache to Redis

Geofence entry/exit state is stored in file cache with 24h TTL. With CACHE_DRIVER=file:
— State is lost on server restart (false alerts on reboot)
— Does not work across multiple app servers

Switch to Redis for both cache and sessions.

🟡 Add Missing DB Indexes

Add a migration with:
(animal_id, recorded_at) on location_history
(status, ends_at) on auctions
managed_by on users
(is_acknowledged, triggered_at) on geofence_alerts

These will eliminate full-index scans on the most common queries.

🟡 Move location_history Cleanup to Scheduler

Deleting 5h-old rows inline with every GPS write adds latency and locks the table during deletes. Move to a scheduled command:
$schedule->command('location-history:prune')->hourly()
Consider increasing retention to 24h for meaningful heatmaps.

🟡 Cache NotificationService Settings

getSetting() hits the DB every call. With 8 calls per alert and sync queue, that's 8 blocking DB round-trips before a single message goes out:

Cache::remember('app_settings', 300, fn() => DB::table('settings')->pluck('value','key')->toArray());

7.2 Medium-Term (Architecture)

Add a Scheduled Task Runner

The kernel's scheduler (app/Console/Kernel.php) appears empty. Register the following commands:
— auctions:expire-payments → hourly
— location-history:prune → hourly
— sanctum:prune-expired → daily
— vaccinations:check-overdue → daily
— tasks:check-overdue → daily

Paginate location_history

GET /animals/{id}/location-history returns all rows for the last N hours with no pagination. For active animals this could be thousands of records per request. Add ->paginate() or ->limit(500) with cursor pagination for the map view.

Migrate Images to Cloud Storage

Animal photos and payment proofs are stored on the local filesystem (public/images/, storage/payment-proofs/). This breaks horizontal scaling and is lost if the server is reprovisioned. Configure FILESYSTEM_DISK=s3 and use S3 or Cloudflare R2 with signed URLs.

Introduce API Resource Caching

Subscription tier listings, species/breed reference data, and user features are read-heavy and change rarely. Wrap them with Cache::tags(['tiers'])->remember() for 10-minute TTL. Bust the cache on admin update.

Fix Auction Bidding Transaction

Wrap bid creation in a pessimistic lock:
DB::transaction(function() use ($auction, $amount, $userId) {
  $auction = Auction::lockForUpdate()->find($id);
  // validate + insert + update current_price
});
This prevents double-bids under concurrent traffic.

Implement Push Notifications

Geofence alerts require the user to open the app to see them. Integrate Firebase Cloud Messaging (FCM) for Android and APNs for iOS. Store device push tokens in a push_tokens table linked to users. Fire push notifications from the queued geofence alert job.

7.3 Long-Term (Architecture Evolution)

✅ GPS Ingestion: Dedicated Microservice or Queue

At scale (thousands of GPS devices pinging every 15s), the current synchronous HTTP endpoint cannot keep up. Consider:
— A dedicated MQTT broker (e.g. Mosquitto/HiveMQ) for device data
— A Go/Node.js consumer writing to location_history at high throughput
— Geofence checks as async workers, not inline HTTP

✅ MySQL Spatial Types for Geofencing

Replace coordinates TEXT with POLYGON GEOMETRY. This unlocks:
— ST_Contains(geofence.polygon, ST_GeomFromText('POINT(lat lng)')) at DB level
— Spatial index (SPATIAL INDEX) for fast zone lookups
— No more PHP ray-casting in application code

✅ Time-Series DB for location_history

Location data is a time-series by nature. A dedicated time-series store (InfluxDB, TimescaleDB) would:
— Handle millions of GPS pings efficiently
— Provide native time-range queries and downsampling
— Eliminate the manual 5h cleanup hack
— Enable analytics like average daily distance

✅ Sanctum Token Expiry + Refresh Tokens

Sanctum tokens currently live forever. Add token expiry in config/sanctum.php:
'expiration' => 60 * 24 * 30 (30 days)
Add a refresh-token flow or re-authentication prompt. Run sanctum:prune-expired daily to clean the tokens table.

✅ API Versioning

No versioning prefix exists. Any breaking change to an endpoint affects all clients simultaneously. Add a route group:
Route::prefix('v1')->group(fn() => require 'api_v1.php');
Mobile clients can pin to v1 while v2 ships with breaking changes.

✅ Read Replica + Connection Management

For production load, configure a MySQL read replica in config/database.php:
'read' => [['host' => env('DB_READ_HOST')]],
'write' => [['host' => env('DB_HOST')]]
All SELECT queries route to the replica automatically, reducing write server pressure.
