B Business

1.1 Product Overview

Oasis (oasis/trace) is a multi-tenant SaaS platform for livestock owners, farms, and herding operations. It delivers real-time GPS tracking, geofence alerting, health record management, team task coordination, and a livestock marketplace (auctions). Arabic-speaking markets are the primary demographic (RTL-first i18n), but the platform supports four languages and is designed for global use.

1.4 Localisation Strategy

The platform supports English (en), Arabic (ar), Urdu (ur), and Basque (eu). Arabic and Urdu use RTL layouts. The i18n implementation is split across three layers:

  • Backend: Language + Translation DB tables + Spatie Translatable on model fields (Geofence.name, Auction.title/description)
  • Frontend: Custom i18n context loading static JS translation files per language
  • Mobile: Custom i18n_service.dart with RTL detection and language switching
Inconsistency: Translations exist in both static files (frontend/mobile) and the database (backend). When content is updated in the DB, the frontend/mobile static files go stale unless manually synced. There is a GET /translations API endpoint that could be used for dynamic translation fetching, but the frontend doesn't appear to use it.

2.2 Schema Observations

  • Dual subscription fields: users.subscription_tier (string) and users.subscription_tier_id (FK) can drift out of sync. Authoritative field is unclear.
  • Species / breed as strings: Animal.species and Animal.breed are plain string columns. The species and breeds tables exist but are not referenced by FKs on animals, so referential integrity is not enforced at the DB level.
  • Geofence coordinates: Stored as a JSON array of [lat, lng] pairs in a standard column, not a MySQL spatial type. Prevents DB-level spatial indexing and ST_Contains queries.
  • Geofence double-decode: getCoordinatesArrayAttribute() calls json_decode() defensively on a field already cast to array, indicating past serialisation bugs.
  • managers() ≡ shepherds(): Both User::managers() and User::shepherds() return hasMany(User::class, 'managed_by') — identical queries, causing semantic confusion.
  • Geofence $translatable without trait: Geofence declares $translatable = ['name'] but does not use the HasTranslations trait — so the directive is silently ignored.
  • Auction second_winner logic: Fallback to second_winner_id is managed entirely in PHP, not enforced by DB constraints.

2.3 Migration Timeline (37 Migrations)

The schema evolved significantly over the project lifetime. Key milestones:

  • Phase 1 (core): users, animals, devices, location_history, geofences, personal_access_tokens
  • Phase 2 (business): auctions, bids, tasks, task_logs — livestock marketplace and workforce management added
  • Phase 3 (health): medical_records, vaccination_schedules — health module added separately
  • Phase 4 (subscriptions): subscription_tiers, user_subscriptions — monetisation layer added post-core
  • Phase 5 (groups & i18n): animal_groups, animal_group_member, animal_group_geofence, languages, translations — batch operations and DB-driven i18n were afterthoughts
  • Role refactor: "Doctor" renamed to "Veterinarian", "Manager" role also changed — applied via a public HTTP route (GET /fix-roles) rather than a migration (see Critical Issues)

3.2 Backend Architecture (Laravel 11)

Controllers are organised under App\Http\Controllers\Api with clean domain sub-namespaces:

Authentication: Sanctum Bearer tokens issued on login, stored in personal_access_tokens. Authorization: Spatie Permission RBAC + a custom limits:{resource} middleware that enforces subscription tier thresholds (max_animals, max_devices, max_users) per user.

3.3 Frontend Architecture (React 18)

The React SPA lives inside the Laravel backend folder. Vite builds output to backend/public/app/, which Laravel serves as static assets under the /app/ base path. Two React Context providers handle global state:

  • AuthContext: Stores Bearer token + user object in browser cookies. Provides login(), logout(), isAuthenticated.
  • PlatformContext: Detects mobile vs desktop viewport for responsive layout adaptation.

A custom apiFetch utility wraps fetch(), injects the Authorization header from cookies, and serialises JSON. There is no Axios, no interceptor pattern, and no centralised error handler — each component handles API errors independently, leading to inconsistent error UX.

Structure Issue: The frontend is co-located inside the backend directory. This makes it hard to run independent CI/CD pipelines, complicates Docker containerisation, and confuses new developers about project boundaries. The frontend should be extracted to its own frontend/ workspace.

3.4 Mobile Architecture (Flutter 3.11)

  • State management: Provider package with AuthProvider (token + auto-login) and DataProvider (shared animals/devices/geofences)
  • Navigation: go_router v14 with a 5-tab bottom navigation bar (Home, Map, Animals, Alerts, Profile)
  • API client: A single monolithic api_service.dart at 1,379 lines covering every domain — a major maintainability concern
  • Maps: flutter_map + latlong2 (OpenStreetMap-compatible, no Google Maps SDK dependency)
  • Auth storage: SharedPreferences — Bearer token stored as plain text on device
  • Offline: No caching or offline-first strategy — app goes dark if API is unreachable
Note: No push notification integration (FCM/APNs) exists in the mobile app. Geofence alerts are only visible when the user manually opens the Alerts tab and the app polls the server. This significantly limits the real-world utility of the alert system.

3.5 Data Flows

Flow A — Animal GPS Location Update

GPS device sends coordinates to POST /api/location-history (currently no auth middleware)

LocationHistoryController stores row in location_history with animal_id, device_id, lat, lng, speed, heading, recorded_at

GeofenceController iterates all active geofences assigned to this animal and runs Geofence::containsPoint() (ray-casting algorithm in PHP)

If violation detected → GeofenceAlert row inserted

Notification sent synchronously via Twilio SMS, WhatsApp Meta API, or SMTP email (all blocking the HTTP request due to sync queue)

Flow B — Auction Payment (Bank Transfer)

Owner lists animal → POST /api/auctions

Bidders compete → POST /api/auctions/{id}/bid; current_price updated on each accepted bid

Owner ends auction → POST /api/auctions/{id}/end; winner_id set, payment_expires_at = now + 48h

Winner uploads bank transfer proof → POST /api/auctions/{id}/payment-proof

Admin reviews and approves/rejects → POST /api/auctions/{id}/verify-payment/{status}

On approval: animal.owner_id transferred to winner. On rejection or payment expiry: second_winner_id is promoted as new winner.

! Inconsistencies & Structural Issues

5.1 Project Layout Anomalies

Critical — Duplicate Directory: D:\animal-trading-v2\backend\backend\ exists as an apparent duplicate of the entire Laravel project, complete with its own vendor/, composer.json, and vite.config.js. This is almost certainly an accidental git commit that doubled the repo size and created a phantom secondary copy of the application. The inner copy should be deleted and added to .gitignore.
Warning — Frontend co-located in backend: The React SPA lives inside the Laravel backend directory (backend/package.json, backend/node_modules/, backend/src/ or resources/js/). Vite builds output to backend/public/app/. This means Laravel and React share one repository folder, complicating independent CI/CD pipelines, Docker layering, and onboarding.

5.2 Route Authentication Gaps

Critical — Public schema mutation route: GET /api/fix-roles is a publicly accessible route (no middleware) that executes raw ALTER TABLE users MODIFY COLUMN role ENUM(...) and bulk UPDATE users SET role = ... statements. Anyone who knows this URL can permanently alter your user roles and DB schema. Delete this route immediately and run the equivalent as a proper database migration.

The following routes are wrapped only in the limits:{resource} middleware — which does not include auth:sanctum. They are effectively public:

6.3 Strengths to Preserve

What's working well: The following patterns are solid and should be maintained as the project matures.
  • Controller namespacing: Clean domain-based sub-namespacing (Auth/, Resources/, Location/, Business/, etc.) — one of the project's strongest architectural decisions
  • Subscription tier limits middleware: Resource gating enforced at the routing layer (not just in controllers) is a clean separation of concern
  • Spatie Permission RBAC: Correctly integrated and extensible — roles are properly seeded and assignable
  • Multi-language architecture: DB-driven translations + RTL support is well-designed and will scale to new languages easily
  • Auction second-winner fallback: Handling the case where the winning bidder fails to pay is a thoughtful real-world edge-case
  • Animal auto-ID (OA-YYYY-NNNN): Human-readable livestock identifiers generated on creation — excellent for field use
  • Task recurrence engine: createNextOccurrence() with configurable recurrence_days is a solid domain model for recurring livestock care tasks
  • Test infrastructure: Both Vitest (unit) and Playwright (E2E) are configured — infrastructure exists even if coverage is low
  • Open-source map stack: flutter_map + Leaflet avoids Google Maps SDK licensing and cost concerns — appropriate for this domain
